# axbt — the Axle Build Tool for Lean 4

`axbt` applies the proven data-pipeline concepts of [dbt](https://www.getdbt.com/) to formal verification in Lean 4: modules are named directories of `.lean` files (the dbt "model" analog), standard `import` statements form a dependency DAG tracked in `manifest.json`, and declarations are addressed as isolated verification targets. Everything is executed through the [Axle (Axiom Lean Engine) API](https://axiommath.ai) via the official [`axiom-axle`](https://pypi.org/project/axiom-axle/) Python SDK — **no local Lean toolchain required**.

## Why

Formal theorem proving in Lean 4 often forces a compromise between monolithic files (slow to check, difficult to isolate) and modular files (fragile, manual import chains and strict scope management). `axbt` bridges the gap:

* **Modules & DAG** — automatic import parsing builds project lineage; declarations are extracted by the real Lean elaborator on the API side.
* **Incremental builds** — MD5 fingerprinting avoids redundant extraction and checking of unchanged files.
* **Rapid feedback tiers** — lightweight typechecking (`axbt check`) is separated from rigorous kernel-level proof verification (`axbt verify`).

## Quick start

Requires Python 3.12+ and [uv](https://docs.astral.sh/uv/).

```bash
git clone https://github.com/dsillman2000/axle-build-tool
cd axle-build-tool
uv sync

# Scaffold a new axbt project anywhere:
uv run axbt init path/to/my-project
```

Point it at your Axle API key (read by the SDK from the environment; request access from [Axiom](https://axiommath.ai)):

```bash
export AXLE_API_KEY=...
```

Then, from inside a project directory, run the pipeline (using `uv run --project <repo>` if you're outside the checkout):

```bash
uv run axbt compile   # scan, extract declarations, write .axbt/
uv run axbt check     # fast typechecking of your targets
uv run axbt verify    # kernel-level proof verification
uv run axbt list      # the parsed declaration tree (offline)
```

A typical `axbt_project.yml` (generated by `axbt init`, then edited):

```yaml
project:
  name: my-project
  version: "0.1.0"

modules:
  my-project:
    targets:          # the default build set for a bare `axbt check`
      - Main.main_theorem

axle:
  environment: lean-4.35.0   # omitted = auto-select the latest the API serves
  timeout_seconds: 120
  global_options:
    maxHeartbeats: 100000
```

## Commands

| Command | Purpose |
| --- | --- |
| `axbt init [PATH]` | Scaffold a new project (config + starter module). |
| `axbt compile` | Scan modules, extract declarations via the API, write `.axbt/manifest.json` and inspectable payloads to `.axbt/compiled/`. |
| `axbt check` | Fast typechecking tier: compile first (incremental by default), then check every configured target — or a `--select`ion — as a standalone payload with dependencies inlined. |
| `axbt verify` | Kernel-level tier: the same machinery, but proofs are checked rigorously against formal statements (theorems only); rejects `sorry` and axiom-based proofs. For final validation, release gates, and CI. |
| `axbt list` | Print the parsed declaration tree — kinds, file-accurate positions, `sorry` markers — dependencies first. Offline and read-only. |
| `axbt debug` | Verify `AXLE_API_KEY` is set and accepted by the API; print the project's configuration and `.axbt/` cache state. |

Run modes (shared by `compile`, `check`, `verify`):

* `--incremental` (default) — re-extract only new and changed files; a clean tree makes no API calls.
* `--full-refresh` — ignore the previous manifest and re-extract everything.
* `--no-compile` (check/verify) — take the existing manifest at face value.

### Selecting what to check

```bash
axbt check --select my-project            # whole module
axbt check --select my-project.Utils      # one file (nested stems allowed: a.b)
axbt check --select my-project.Utils.x    # one declaration, dependency subgraph inlined
```

The first segment matches a module, the next greedily matches a file stem, and the remainder matches extracted declaration names (full or unique-suffix). Declaration-level checking/verification resolves theorems and lemmas; definitions are checked by selecting their file or module.

## Project layout

```
axbt_project.yml      # project + modules + axle settings
M/…                   # module source directories (`.lean` files)
.axbt/                # cache (gitignore it):
  manifest.json       #   the DAG: nodes, md5 fingerprints, extraction metadata
  compiled/           #   the exact standalone payloads submitted to the API
```

## Development

```bash
uv sync
uv run pytest                    # offline suite (fakes; CI's gate)
AXLE_API_KEY=… uv run pytest -m live   # live suite against the real API
```

CI runs the offline suite on every PR, the live suite and the demo pipeline (`compile && check && verify` per demo) on every PR and push to `main`.
