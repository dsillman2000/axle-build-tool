# axbt — the Axle Build Tool for Lean 4

`axbt` applies the proven data-pipeline concepts of [dbt](https://www.getdbt.com/) to formal verification in Lean 4: modules are named directories of `.lean` files (the dbt "model" analog), standard `import` statements form a dependency DAG tracked in `manifest.json`, and declarations are addressed as isolated verification targets. Everything is executed through the [Axle (Axiom Lean Engine) API](https://axiommath.ai) via the official [`axiom-axle`](https://pypi.org/project/axiom-axle/) Python SDK — **no local Lean toolchain required**.

## Why

Formal theorem proving in Lean 4 often forces a compromise between monolithic files (slow to check, difficult to isolate) and modular files (fragile, manual import chains and strict scope management). `axbt` bridges the gap:

* **Modules & DAG** — automatic import parsing builds project lineage; declarations are extracted by the real Lean elaborator on the API side.
* **Incremental builds** — MD5 fingerprinting avoids redundant extraction and checking of unchanged files.
* **Rapid feedback tiers** — lightweight typechecking (`axbt check`) is separated from rigorous kernel-level proof verification (`axbt verify`).

## Quick start

`axbt` is a `uv` tool: [uv](https://docs.astral.sh/uv/) (Python 3.12+) is the only requirement, and it is the intended way to install and run axbt — no checkout of this repo, and no local Lean toolchain needed.

```bash
# The main way: install as a uv tool from the repo, then use `axbt` anywhere.
uv tool install git+https://github.com/dsillman2000/axle-build-tool
uv tool upgrade axle-build-tool   # later: pick up new commits from the repo

# One-shot form without installing anything (e.g. for CI scripts):
uvx --from git+https://github.com/dsillman2000/axle-build-tool axbt <command>
```

Scaffold a new project """

Bash:

```bash
# Scaffold a new axbt project anywhere:
axbt init path/to/my-project
```

Point it at your Axle API key (read by the SDK from the environment; request access from [Axiom](https://axiommath.ai)):

```bash
export AXLE_API_KEY=...
```

Then, from inside a project directory, run the pipeline:

```bash
axbt build   # check + verify in one run (or run the tiers individually)
axbt compile # scan, extract declarations, write .axbt/
axbt check   # fast typechecking of your targets
axbt verify  # kernel-level proof verification
axbt list    # the parsed declaration tree (offline)
```

(Inside a checkout of this repository itself, the same commands run via `uv run axbt …` — see [Development](#development).)

A typical `axbt_project.yml` (generated by `axbt init`, then edited):

```yaml
project:
  name: my-project
  version: "0.1.0"

modules:
  my-project:
    targets:          # the default build set for a bare `axbt check`
      - Main.main_theorem

axle:
  environment: lean-4.35.0   # omitted = auto-select the latest the API serves
  timeout_seconds: 120
  global_options:
    maxHeartbeats: 100000
```

## Commands

| Command | Purpose |
| --- | --- |
| `axbt init [PATH]` | Scaffold a new project (config + starter module). |
| `axbt compile` | Scan modules, extract declarations via the API, write `.axbt/manifest.json` and inspectable payloads to `.axbt/compiled/`. |
| `axbt check` | Fast typechecking tier: compile first (incremental by default), then check every configured target — or a `--select`ion — as a standalone payload with dependencies inlined. Clean outcomes are recorded per declaration in the manifest. |
| `axbt verify` | Kernel-level tier: the same machinery, but proofs are checked rigorously against formal statements (theorems only); rejects `sorry` and axiom-based proofs. For final validation, release gates, and CI. Successful verifications are recorded separately from check outcomes. |
| `axbt build` | Both tiers in one run, dbt-style: the check tier streams first, then the verify tier — skipping the selections whose check failed — and the run exits nonzero if either tier failed. Verdict rows carry a `[check]`/`[verify]` tier suffix so the two passes tell apart. |
| `axbt list` | Print the parsed declaration tree — kinds, file-accurate positions, `sorry` markers — dependencies first. Offline and read-only. |
| `axbt graph` | Render the manifest as an offline, interactive Cytoscape.js HTML graph (default `.axbt/graph.html`; `--select` filters the subgraph). Colors key on outcome stamps only. No API calls. |
| `axbt debug` | Verify `AXLE_API_KEY` is set and accepted by the API; print the project's configuration and `.axbt/` cache state. |

Run modes (shared by `compile`, `check`, `verify`, `build`):

* `--incremental` (default) — re-extract only new and changed files; a clean tree makes no API calls.
* `--full-refresh` — ignore the previous manifest and re-extract everything.
* `--no-compile` (check/verify/build) — take the existing manifest at face value.
* `--fail-fast` / `-x` (check/verify/build) — stop at the first failing selection: cancel all ongoing submissions and report the failure instead of finishing the run. The summary counts what was not judged (`2 cancelled by fail-fast`); under `build`, a fail-fast in the check pass ends the build before the verify pass.
* `--sorry <selector>` (repeatable) — grant a dependency subtree: theorem proof bodies become `sorry` stubs in the submitted payload (signatures intact), and the granted declarations are excused — skipped under check, auto-permitted under verify. Def/abbrev bodies stay real: they are definitional content that downstream proofs unfold (anonymous constructors, projections, `rfl`), so stubbing them would break the very elaboration the grants are meant to leave working. Verify theorems against trusted dependency signatures, or check without paying for slow or broken upstream proofs.
* `--minify/--no-minify` (check/verify/build) — payload minification is on by default: comments and blank lines are stripped from the submitted content (declaration docstrings and indentation stay put), shrinking request bodies and the `.axbt/compiled/` inspection artifacts. Attribution is unaffected — line maps are built from the surviving lines' original numbers, and files that don't track cleanly are submitted unminified. `--no-minify` opts a run out; set `minify: false` under `project:` in `axbt_project.yml` to change the default. The cached/stamped signature material includes the effective setting, so flipping the mode re-verifies once under the new payload shape.

### Building both tiers

`axbt build` runs the two tiers over the same selections in one invocation — dbt's combined "run + test": the check tier streams first, then the verify tier, then the run exits nonzero if either tier failed. Selections whose check failed are skipped (without a submission) in the verify pass — re-verifying them would only repeat the failure — and a fail-fast in the check pass abandons the build before verifying anything. Every build-mode verdict row carries its tier as a suffix so the two reports tell apart:

```text
18:44:29.123 [ 1/2] M.A.t1  START  [RUN]
18:44:29.530 [ 1/2] M.A.t1  OK  0.407s  [check]
18:44:29.531 [ 2/2] M.B.t2  START  [RUN]
18:44:29.533 [ 2/2] M.B.t2  FAIL  0.002s  [check]
18:44:29.540 Checked 2 selection(s): 1 failed, 1 OK in 0.412s
18:44:29.601 [ 2/2] M.B.t2  SKIP  [verify]
    the check pass failed this selection above; verify skipped
18:44:29.602 [ 1/2] M.A.t1  START  [RUN]
18:44:29.602 [ 1/2] M.A.t1  OK  0.712s  [verify]
18:44:29.715 Built 2 selection(s): 1 failed, 1 OK in 0.592s
```

`build` shares every run mode: `--sorry` grants apply in the check pass, `--permitted-sorries`/`--force` shape the verify pass, and `--select`, `--share`, `--fail-fast`, and the minification settings apply to both.

### Streaming results

`axbt check` / `axbt verify` print each result the moment its submission completes — in completion order, so progress appears live during long runs. Every submission also announces itself dbt-style with a white `START` line the moment it is actually dispatched (dispatch order under the concurrency bound; selections answered locally — skips, cached verifications, `--sorry` grants — submit nothing and print no START):

```text
14:22:04.183 [ 1/2] M.A.t1  START  [RUN]
14:22:04.185 [ 2/2] M.B.t2  START  [RUN]
14:22:04.492 [ 1/2] M.A.t1  OK  0.312s
14:22:05.725 [ 2/2] M.B.t2  FAIL  1.234s
    [line 3, col 5 of M/B.lean] ...
14:22:05.726 [ 3/3] M.C.t3  SKIP
14:22:05.730 Checked 3 selection(s): 1 failed, 2 OK in 1.589s
```

* Every report line carries an aligned `HH:MM:SS.mmm` timestamp, and the item-indexed `[n/m]` counter is shared by a selection's START and its verdicts (dbt pairing) — verifications answered locally (skips, cached selections, `sorry` failures) print under their index first, without their own START.
* Timings measure each submission individually — from its own START to its verdict — so waiting on the concurrency limit doesn't hide in them.

### Sharing a run

`axbt check --share` / `axbt verify --share` print a share link for every submission — a URL to the Axle web app showing that exact run (source, messages, verdict). The route names the platform tool that served the request: check runs link to the check UI, verify runs (including the cached-selection links) to the verify_proof UI:

```text
14:22:10.021 [ 1/1] M.User.derived_holds  OK  0.42s
    share: https://axle.axiommath.ai/check#r=e00f26e7-b2b6-47b2-9197-0dd5518434ec
```

* Sharing is best-effort: a failed mint prints a dim warning and never changes the exit code.
* `verify --share` also links each cached selection to its most recent recorded verification (marked "(from the earlier run)") — no re-submission; its link opens the verify_proof UI like every verify mint.
* Sharing writes nothing to the manifest; links live in the transcript where you copy them from.

### Outcome records in the manifest

The manifest records three kinds of per-declaration facts (all additive, optional fields — old manifests load unchanged, and new runs backfill them):

* **Dependencies** (`compile`) — every extracted declaration carries `dependencies` (the deduplicated, sorted union of the API's local type/value/syntactic dependency lists; declaration names as the API reports them, cross-file edges included) and `external_dependencies` (names outside the project — tooltip material, not graph nodes).
* **Check stamps** (`check`) — a payload that passed clean stamps every declaration it judged with `checked_sig`/`checked_at`/`checked_request_id`. The signature covers the file dependency closure's content, the resolved environment, and the global options — the same key material the verify cache uses. `--sorry`-stubbed and failing payloads record nothing.
* **Verify stamps** (`verify`) — kernel-level successes get `verified_sig`/`verified_at`/`verified_request_id`. They are consulted by the verify cache and never by check's records.

The two tiers are distinct facts: a `sorry` passes check and fails verify, so `checked_sig` without `verified_sig` means "checked-clean, still awaiting kernel verification" — the state the per-declaration status graph renders as its "in progress" color.

### Visualizing the manifest

`axbt graph [--select SELECTOR] [-o PATH]` renders `.axbt/manifest.json` as a single-file
Cytoscape.js HTML visualization — pan/zoom, hover tooltips, click to highlight a node's
neighborhood. Declaration level: every declaration is a node under its file, under its module,
with file import edges and declaration-to-declaration edges from the extracted dependency lists.

```bash
axbt graph                              # whole manifest -> .axbt/graph.html
axbt graph --select my-project.Utils    # one file + its dependency closure
```

Colors are read straight from the manifest's per-declaration outcome stamps — nothing is inferred:

* **green = verified** — `verified_sig` present (kernel-level), or **done**: a checked-clean
  declaration of a never-verifiable kind (defs, instances, structures — a clean check is their
  final tier, so they read the same green).
* **yellow = checked** — `checked_sig` present but not verified: passed `check`, awaiting `verify`.
* **orange = unchecked** — neither stamp: never judged by a full, unstubbed check.
* Containers roll up to the weakest constituent color; declaration-free files/modules are grey.

Files whose source is `new`/`changed` carry a red ✱. The only external asset is the
Cytoscape.js script from a pinned CDN URL — nothing is fetched by axbt itself, and the
command makes no API calls.

### Selecting what to check

```bash
axbt check --select my-project            # whole module
axbt check --select my-project.Utils      # one file (nested stems allowed: a.b)
axbt check --select my-project.Utils.x    # one declaration, dependency subgraph inlined
```

The first segment matches a module, the next greedily matches a file stem, and the remainder matches extracted declaration names (full or unique-suffix). Declaration-level checking/verification resolves theorems and lemmas; definitions are checked by selecting their file or module.

## Project layout

```
axbt_project.yml      # project + modules + axle settings
M/…                   # module source directories (`.lean` files)
.axbt/                # cache (gitignore it):
  manifest.json       #   the DAG: nodes, md5 fingerprints, extraction metadata
                      #   (compact single-line JSON; inspect via `python -m json.tool`)
  compiled/           #   the exact standalone payloads submitted to the API
                      #   (minified by default, like the submissions)
```

## Development

```bash
uv sync
uv run pytest                    # offline suite (fakes; CI's gate)
AXLE_API_KEY=… uv run pytest -m live   # live suite against the real API
```

CI runs the offline suite on every PR, the live suite and the demo pipeline (`compile && check && verify` per demo) on every PR and push to `main`.

See the GitHub issues for the phase-by-phase history.
